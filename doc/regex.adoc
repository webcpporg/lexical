[#lexical-regex]
== Regular expressions

`is_regex` answers whether a string is a regular expression, JSON Schema's
`regex`: ECMA-262's `Pattern` in `u` mode, with ECMAScript 2025's modifiers,
`+(?i:...)+`, and its duplicate group names, `+(?<y>...)|(?<y>...)+`. It is
declared in `<webcpp/lexical/regex.hpp>`, the one header of lexical that
brings the Unicode tables of ECMA-262's classes: `<webcpp/lexical.hpp>` leaves
it out, and a program that never validates a pattern does not compile them.

[source]
----
include::{examples}/lexical_regex.cpp[tag=program,indent=0]
----

It prints:

[listing]
----
include::{examples}/lexical_regex.expected[]
----

[#lexical-regex-how]
=== How a pattern is judged

A pattern is valid when ECMA-262 accepts it as a `Pattern` in `u` mode, early
errors included: when `new RegExp(pattern, "u")` does not throw a
SyntaxError. lexical's validator reads the pattern as that grammar reads it,
and refuses what the grammar refuses there: Annex B's escapes and classes,
`\a`, `\-` outside a class, `\8`, an octal escape; Perl's `\A`, `\Z` and `\z`;
a group of another dialect, `+(?P<n>...)+`, `+(?#...)+`, a leading `(?i)`; a
property ECMA-262 does not name, as `+\p{letter}+` or `+\p{Script=Foo}+`; a
backreference to a group the pattern does not hold; two groups of one name
that a match could both hold. A pattern that is not well-formed UTF-8 is
refused, and a NUL is a literal like any other code point.

Valid means that the syntax and the early errors accept the pattern, and
nothing more. `is_regex` compiles no pattern and runs none: it says nothing of
how long a matcher takes on a valid pattern, nor of the limits an engine sets
on the program it builds from one. The property names `+\p{...}+` accepts are
Unicode {unicode-version}'s, read from the generated tables
(<<lexical-regex-tables>>): no ICU and no `std::locale`.

ECMA-262 allows a lookbehind of any width, `+(?<=\$\d*)+`, and so does
`is_regex`: it never measures a lookbehind, since it compiles nothing.

`is_regex` has no rule: a pattern has no grammar of its own inside a longer
input, so `is_regex` judges a whole string.

[#lexical-regex-bounds]
=== Bounds

Two bounds keep a hostile pattern, which JSON Schema meets in an instance,
from taking the stack or the time of a program. Past one of them, `is_regex`
answers `false` without judging the pattern, though ECMA-262 may allow it:

[%header,cols="2,1,5"]
|===
| Constant | Value | Bounds
| `max_regex_length` | 65,536 | a pattern's bytes, refused before they are read: the validator reads parts of a pattern again, so a bound on its length bounds its time
| `max_regex_nesting` | 32 | groups, lookarounds and modifiers one inside the other: the validator descends into a group by calling itself, so the nesting bounds its stack
|===

[#lexical-regex-allocation]
=== What it allocates

`is_regex` allocates nothing, on any target. It takes no memory resource: its
reader works on the pattern's own bytes and keeps its state on the stack, to
the depth `max_regex_nesting` allows. So `<webcpp/lexical/regex.hpp>` keeps
lexical's rule that a validator allocates nothing, as the allocation table says
(<<lexical-allocation>>).

[#lexical-regex-v8]
=== Compared with V8

A test of lexical, `regex_v8`, compares `is_regex` with V8 on
{n-regex-patterns} patterns, of which {n-regex-valid} are valid by V8's
verdict. The patterns are drawn at random, from seeds 2 to 9 of Python's
`random.Random`, from a grammar of atoms, groups of every kind,
backreferences, assertions, quantifiers and defects; every name `+\p{...}+`
accepts, under each of its forms, and the same names misspelt; every pattern
the JSON-Schema-Test-Suite's schemas hold, in `pattern` and `patternProperties`,
and every string of its tests of the format `regex`; and the cases the grammar
does not draw: ECMAScript 2025's modifiers and duplicate group names,
lookbehinds of every width, escapes of every kind, and classes and quantifiers
at their edges. V8's verdict is `new RegExp(pattern, "u")` throwing a
SyntaxError or not, written by the oracle of `test/oracle`, which runs the
pinned Node, 26.7.0, whose V8 is 14.6 and whose Unicode is 17.0. On each of
these patterns the verdict of `is_regex` is V8's, on every target
(<<lexical-testing>>).

To check the committed verdicts against the pinned Node, and `is_regex`
against them:

[source,bash]
----
b2 -a libs/lexical/test/oracle//oracle
b2 -a libs/lexical/test//regex_v8
----

After a change to the patterns, `update-expected` writes the verdicts again:

[source,bash]
----
b2 libs/lexical/test/oracle//update-expected
----

[#lexical-regex-tables]
=== The Unicode tables

`tools/generate_tables.py`, in lexical's repository, writes
`<webcpp/lexical/detail/regex_tables.hpp>` from Unicode's data files of
version {unicode-version}, pinned in `tools/unicode.json`, each by its URL
under `\https://www.unicode.org/Public/{unicode-version}/` and its SHA-256: a
file its cache lacks is downloaded, every file is hashed, and a digest that
differs stops it before it writes anything. Before it writes, it checks what
the validator and the traits assume of the data: General_Category has 30
values that are no group; every value a file holds is one
`PropertyValueAliases.txt` names; each of ECMA-262's binary properties holds
a code point; every name is ASCII and names one value; the classes fit the
traits' mask; and no simple case folding orbit holds more than four code
points. A script that no code point has, Katakana_Or_Hiragana, gets no name,
as ECMA-262's table of the values of Script leaves it out.
`tools/generate_patterns.py` writes the patterns `regex_v8` reads, the same
way.

The own lane `generated` runs both generators again, into the build
directory, and compares each output with the committed file, byte for byte;
`update-generated` writes them in place, the one writer of the generated
files. The ordinary lanes never run them, since a generator may need the
network. The data are Unicode's, under the Unicode License v3, whose notice
is in <<lexical-unicode-data,the appendix "Unicode data">>.

[source,bash]
----
b2 -a libs/lexical/test//generated
b2 libs/lexical/test//update-generated
----
